# 🇸🇬 Singapore Travel Assistant

An AI-powered **Singapore Travel Assistant** built with **RAG (Retrieval-Augmented Generation)**, **ChromaDB**, **Llama 3.1 8B**, **MCP (Model Context Protocol)**, and **Streamlit**.

The assistant provides grounded Singapore travel information using a curated local Knowledge Base and can dynamically use external MCP tools for:

* 🌦️ Weather and forecasts
* 💱 Currency conversion
* 📚 Singapore travel knowledge
* 🗺️ Weather-aware itinerary planning
* 💬 Conversation history

The system is designed to prevent unsupported Singapore-specific information from being generated by requiring destination facts to come from the retrieved Knowledge Base.

---

## ✨ Features

### 📚 Retrieval-Augmented Generation

The assistant uses a local Singapore travel Knowledge Base containing information from multiple travel documents.

The documents are:

* Singapore city-in-nature information
* Culture and heritage
* Dining
* Essential travel information
* Family activities
* Iconic architecture
* Itineraries
* Museums and galleries
* Neighbourhoods
* Nightlife
* Shopping
* Unique experiences
* Wikivoyage Singapore

The documents are split into chunks, embedded, and stored in **ChromaDB**.

For each user query:

```text
User Question
      ↓
Intent Detection
      ↓
RAG Retrieval
      ↓
Relevant Chunks
      ↓
LLM
      ↓
Grounded Answer
```

---

## 🌦️ Weather MCP

The assistant can connect to a dedicated Weather MCP server.

The weather server provides:

* Current temperature
* Feels-like temperature
* Humidity
* Precipitation
* Minimum temperature
* Maximum temperature
* Rain probability
* Forecast rainfall

Weather information is retrieved dynamically rather than being stored in the Knowledge Base.

When an itinerary is requested, the forecast can influence the ordering and selection of Knowledge Base-supported activities.

---

## 💱 Currency MCP

The assistant also provides currency conversion through a dedicated Currency MCP server.

Examples:

```text
50000 INR to SGD
100 USD in SGD
250 EUR to SGD
```

The assistant extracts:

* Amount
* Source currency
* Target currency

and passes those values to the Currency MCP server.

The conversion result returned by the MCP server is then provided to the LLM.

---

## 🧠 Intent Detection

The system uses deterministic rule-based intent detection.

Supported intent types:

```text
RAG
WEATHER
CURRENCY
RAG + WEATHER
RAG + CURRENCY
RAG + WEATHER + CURRENCY
UNKNOWN
```

The intent detector determines whether the question requires:

* Knowledge Base retrieval
* Weather MCP
* Currency MCP
* A combination of these

Example:

```text
"What should I do in Singapore?"
```

→ `RAG`

```text
"What will the weather be like in Singapore?"
```

→ `WEATHER`

```text
"Plan a Singapore trip based on the weather."
```

→ `RAG + WEATHER`

```text
"How much is 50000 INR in SGD?"
```

→ `CURRENCY`

```text
"Plan a 5-day Singapore trip based on weather and my INR budget."
```

→ `RAG + WEATHER + CURRENCY`

# 📂 Main Components

## `app/agent/`

Contains the main travel-agent orchestration logic.

### `travel_agent.py`

The central component of the application.

It:

1. Detects user intent
2. Determines itinerary duration
3. Retrieves Knowledge Base information
4. Connects to MCP servers when required
5. Calls Weather MCP
6. Calls Currency MCP
7. Builds the LLM prompt
8. Generates the final response
9. Maintains conversation history

### `intent.py`

Contains deterministic intent detection.

It identifies:

```text
RAG
WEATHER
CURRENCY
RAG + WEATHER
RAG + CURRENCY
RAG + WEATHER + CURRENCY

```

This determines which backend components are required for a question.

Defines the state passed through the travel agent.

The state contains:


This keeps the different pieces of information available during response generation.

Responsible for building the RAG context.

It:

# 📚 RAG Components

## `app/rag/`

Contains the Retrieval-Augmented Generation pipeline.

### `embeddings.py`

Provides the embedding model used to convert text into vectors.

Conceptually:

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

---

### `ingest.py`

Responsible for loading the Singapore Knowledge Base and storing it in ChromaDB.

The ingestion process is:

```text
Markdown files
      ↓
Document loading
      ↓
Chunking
      ↓
Embeddings
      ↓
ChromaDB
```

Run ingestion whenever the Knowledge Base is rebuilt or changed.

---

### `retriever.py`

Responsible for similarity search against ChromaDB.

The current retrieval function uses:

```python
vector_store.similarity_search(
    query,
    k=k,
)
```

The value of `k` controls how many chunks are returned.

Important:

> `k` represents retrieved chunks, not unique source documents.

For example:

```text
k = 100
```

can return 100 chunks that may originate from only a smaller number of source documents.

---

### `generator.py`

Contains generation-related RAG functionality.

---

### `qa.py`

Contains Knowledge Base question-answering functionality and related RAG testing/logic.

# 🔎 How Retrieval Works

Suppose the user asks:

```text
"What are some cultural places I can visit in Singapore?"
```

The query is converted into an embedding:

```text
"What are some cultural places..."
             ↓
       Query Vector
```

The query vector is compared against the vectors stored in ChromaDB.

The chunks are ranked according to vector distance/similarity.

The top `k` chunks are returned:

```text
Query
 ↓
Embedding
 ↓
Vector similarity search
 ↓
Ranked chunks
 ↓
Top K chunks
 ↓
LLM context
```

The system then supplies those chunks to Llama 3.1 8B.

---

# 🧩 Chunking

The Knowledge Base is not stored as one large document per source.

Documents are divided into smaller chunks.

For example:

```text
visitsingapore_culture_heritage.md
              ↓
        Chunk 1
        Chunk 2
        Chunk 3
        Chunk 4
              ↓
         Embeddings
              ↓
           ChromaDB
```

This allows the retriever to find specific sections relevant to the user's question.

Multiple chunks can belong to the same source document.

Therefore:

```text
100 retrieved chunks
```

does **not** mean:

```text
100 sources
```

The application normalizes the source metadata before presenting sources to the user.

---

# 🌦️ Weather-Aware Itineraries

For itinerary questions involving weather, the system combines:

```text
Knowledge Base
      +
Weather MCP
      ↓
Llama 3.1 8B
      ↓
Weather-aware itinerary
```

For example, if the Weather MCP returns a high rain probability for a particular day, the LLM is instructed to prioritize Knowledge Base-supported activities that are less affected by rain where suitable information is available.

The system does not invent weather values.

The weather values supplied by the MCP are treated as authoritative for the generated response.

---

# 💱 Currency Processing

For currency-related questions, the system extracts the requested conversion.

Example:

```text
Convert 50000 INR to SGD
```

The extraction process identifies:

```text
Amount: 50000
From: INR
To: SGD
```

The values are passed to:

```text
Currency MCP
```

The MCP result is then included in the LLM context.

The agent does not independently calculate an exchange rate.

---

# 💬 Conversation Memory

The `TravelAgent` maintains recent conversation history.

The assistant stores:

```text
User message
Assistant response
```

and retains the most recent conversation entries.

This allows follow-up questions such as:

```text
User:
Plan a 3-day Singapore trip.

Assistant:
...

User:
Make day 2 more suitable for rain.
```

The previous conversation can be supplied to the LLM as context.

# 🛡️ Grounding Rules

The assistant is designed to minimize hallucinated Singapore-specific information.

The generation prompt instructs the model to follow these principles:

### Destination facts

Singapore-specific attractions and travel facts should come from the retrieved Knowledge Base.

### Weather

Weather values should come from Weather MCP when it is called.

### Currency

Currency conversion results should come from Currency MCP when it is called.

### Missing information

If the Knowledge Base does not contain enough information, the assistant should indicate that the information is unavailable rather than filling the gap with unsupported facts.

### Sources

Only retrieved Knowledge Base sources should be presented as sources.

### Recommendations

The response distinguishes between:

```text
Knowledge Base facts
MCP information
AI-generated recommendations
```

The itinerary structure itself is considered an AI-generated recommendation, even when the individual activities come from the Knowledge Base.

# 📌 Important Design Decisions

## Local Knowledge Base

Singapore destination information is grounded in a local Knowledge Base instead of relying solely on the LLM's pretrained knowledge.

## Deterministic Intent Detection

Intent detection uses explicit keyword-based rules rather than asking the LLM to determine which tools should be called.

## Tool Separation

Weather and currency operations are separated into MCP servers.

## Source Tracking

Retrieved chunks carry source metadata so the final response can identify the Knowledge Base documents actually retrieved.

## Conversation Context

Recent conversation history is retained to support follow-up questions.

## Dynamic Currency Extraction

Currency requests are parsed from the user's question rather than using a fixed test conversion.

## Variable Itinerary Length

The assistant extracts itinerary duration from the question and supports itinerary lengths within the configured range.

# ⚠️ Limitations

* The intent detector is rule-based and depends on its keyword lists.
* RAG quality depends on the quality of document chunking and embeddings.
* Retrieval quality depends on the selected `k` value.
* The LLM can only ground Singapore-specific claims to the retrieved context supplied to it.
* Weather information depends on the Weather MCP service.
* Currency conversion depends on the Currency MCP service.
* The current system is focused specifically on Singapore travel.
* Conversation memory is maintained in application memory and is not a persistent user database.
